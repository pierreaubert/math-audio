# Analog coloration and hardware-modeling library plan — 2026-08-13

## Status

Planning document only. No production implementation is authorized by this
document. Before coding begins, create or identify the corresponding issue as
required by the SOTF repository workflow.

The existing Saturation plugin review in
`reviews/20260812-plugin-saturation.md` remains the source of truth for that
plugin's correctness and remediation work. This plan does not reopen those
findings. It defines a reusable DSP library and a staged integration path for
adding optional analog coloration to selected plugins.

## Objective

Build a reusable, host-independent Rust library for:

1. A controlled second/third-harmonic generator that serves as the simple,
   cheap comparison baseline.
2. Static analog-flavoured waveshaping with explicit, truthful mathematical
   contracts.
3. Frequency-dependent and stateful coloration that can reproduce measured
   behavior of old analog equipment.
4. Eventual component- or circuit-level models where a schematic or measured
   reference unit justifies the additional complexity.

The library must be suitable for SOTF's realtime audio path: bounded work,
allocation-free steady-state processing, deterministic reset, explicit
latency, multichannel isolation, sample-rate-aware state, and safe host
automation.

## Non-goals

- Do not claim that a `tanh` or polynomial curve is a physical tube, tape, or
  transformer emulation.
- Do not add noise, hum, crosstalk, wow, or flutter unconditionally. These
  defects must be separate controls and default to off.
- Do not put SOTF parameter IDs, UI metadata, serialization, presets, or host
  graph types in the mathematical DSP crate.
- Do not implement a general unbounded Newton solver on the audio thread.
- Do not place an identical coloration wrapper around every plugin without
  deciding whether the stage belongs before, after, or inside the plugin's
  control loop.
- Do not introduce `unsafe`.

## Existing baseline

The current `sotf-plugin-saturation` implementation already provides useful
building blocks:

- normalized `tanh` soft clipping;
- odd-symmetric Tube-labelled static waveshaping;
- a Tape-labelled memoryless exponential sigmoid, explicitly documented as
  not implementing hysteresis;
- split-band excitation;
- per-channel ADAA state for supported memoryless nonlinearities;
- envelope-dependent drive;
- DC blocking, parameter smoothing, output trim, and dry/wet mixing;
- host-owned oversampling and latency reporting.

The low-level ADAA implementation is already owned by `math-dsp` and exposed
through `sotf-host`. The new library must reuse that implementation rather
than create a competing antialiasing path.

The existing Tube and Tape modes are useful coloration curves, but they are
not hardware models. Preset compatibility requires retaining their existing
identities and indices; stronger models must use new names or append-only
model identifiers.

## DSP classification and convention

The processing is discrete-time, causal, deterministic for a fixed parameter
stream, nonlinear, and potentially time-varying/stateful.

Use normalized full-scale floating-point audio:

- input and output samples are `f32`;
- nominal full scale is `[-1, 1]`, but the implementation must remain finite
  for finite out-of-range input;
- frequency parameters use Hz;
- time parameters use milliseconds;
- level controls use dB;
- default analog calibration is proposed as `0 VU = -18 dBFS`;
- channel data is interleaved in SOTF integration;
- each channel owns independent nonlinear and dynamic state unless a model
  explicitly exposes stereo linking or crosstalk.

The general model is:

```text
u[n] = H_pre { g_in * x[n] }
v[n] = F(u[n], state[n])
state[n + 1] = G(u[n], state[n])
y[n] = g_out * H_post { v[n] }
```

where `H_pre` and `H_post` are linear conditioning filters, `F` is the
nonlinear stage, and `G` updates optional memory such as sag, magnetic flux,
hysteresis, slew, or an envelope-dependent operating point.

The simple harmonic generator is the special case with identity filters and
no state.

## Harmonic baseline

Implement an explicit `Harmonics` model so that every richer model can be
compared against a cheap, explainable reference.

For a normalized input `u`, use an orthogonal polynomial basis:

```text
T2(u) = 2*u^2 - 1
T3(u) = 4*u^3 - 3*u
v = u + h2*T2(u) + h3*T3(u)
```

For a unit-amplitude cosine inside `[-1, 1]`, `T2` and `T3` produce exact
second and third harmonics. At other amplitudes and on programme material,
they also create DC and intermodulation products. The implementation must:

- define behavior outside the normalized fitting interval;
- use a smooth bounded input mapping rather than allowing unbounded polynomial
  growth;
- preserve a known small-signal gain;
- remove or analytically center generated DC;
- provide a final DC blocker as a safety invariant;
- expose independent H2 and H3 levels in dB relative to the fundamental;
- include calibrated input drive and output trim;
- document that the controls describe nonlinear branch strength, not an
  independent spectral synthesizer.

An odd-symmetric transfer function, `F(-x) = -F(x)`, produces only odd
harmonics for a symmetric single-tone input. Controlled even harmonics require
asymmetry or bias. Real single-ended and push-pull tube stages behave
differently, so “tube equals second harmonic” must not become an API
assumption.

## Recommended model hierarchy

### Tier 0 — Harmonics

Purpose: scientific baseline and very low-cost “warmth” control.

- H2 and H3 controls;
- calibrated drive/reference level;
- bounded output and DC removal;
- ADAA or oversampling as selected by measurement;
- no claims of hardware emulation.

### Tier 1 — Static coloration

Purpose: consolidate the existing useful memoryless curves.

- symmetric soft clipping;
- asymmetric/bias-controlled shaping;
- selectable knee/curve;
- normalized small-signal gain;
- optional pre/post tilt filters;
- closed-form antiderivatives where ADAA is used.

Names must describe the curve or say “-style”; documentation must explicitly
state that these are memoryless waveshapers.

### Tier 2 — Measured Wiener/parallel-Hammerstein models

Purpose: the preferred first implementation for convincing analog character.

Use:

```text
y[n] = sum(k=1..K) H_k { phi_k(u[n]) }
```

where `phi_k` are bounded polynomial/Chebyshev branches and `H_k` are short
filters fitted from measurement. Start with `K <= 5`.

This tier can reproduce frequency-dependent harmonic level and phase while
keeping CPU, latency, and state predictable. The H2/H3 baseline is a special
case with constant branch filters, which makes the comparison direct.

Candidate first model: `Console` or `Preamp`, consisting of:

- calibrated input stage;
- coupling high-pass response;
- mild frequency-dependent asymmetry;
- level-dependent compression;
- high-frequency output pole;
- optional slow envelope-dependent operating point;
- level-matched output.

Use branded or hardware-specific names only when the model was fitted and
validated against that reference unit.

### Tier 3 — Stateful physical models

Purpose: capture behavior that memoryless and Hammerstein models cannot.

Potential models:

- transformer flux/magnetization and low-frequency saturation;
- tape hysteresis, record/replay EQ, head bump, and level-dependent HF loss;
- power-supply sag;
- slew-rate limiting;
- bias-dependent asymmetric stages;
- wow/flutter, noise, hum, and crosstalk as optional modules.

Wave Digital Filters or bounded state-space integration are preferred for
component models. Any iterative nonlinear solve must have:

- a strict iteration cap;
- deterministic convergence criteria;
- a finite, click-safe fallback;
- no allocation or logging in processing;
- stress tests for extreme state and parameter values.

Do not begin this tier without a schematic, a measured reference unit, or a
clearly documented stylized target.

## Crate and ownership design

Create a new `math-analog` crate in the `math-audio` repository rather than
placing hardware models in `sotf-host`.

Proposed ownership:

### `math-dsp`

- existing ADAA primitives;
- generic filters, smoothing, envelopes, denormal helpers, and oversampling
  primitives already owned there;
- no hardware-specific presets or SOTF host types.

### `math-analog`

- calibrated gain/reference-level mapping;
- harmonic and static waveshapers;
- pre/post filter chains;
- per-channel model state;
- Hammerstein branches and measured model coefficients;
- optional stateful physical models;
- model-level reset, latency, and processing contracts;
- offline response-analysis helpers only when they do not burden the runtime
  dependency; otherwise keep these under tests/benches.

### `sotf-host`

- graph-level oversampling ownership;
- latency compensation;
- topology rebuild and safe graph-boundary swap;
- host automation and update-mode enforcement;
- no model-specific signal equations.

### SOTF plugin wrappers

- parameter IDs, schema, ranges, units, UI layout, and serialization;
- append-only mode identifiers and preset migration;
- mapping host parameters to model targets;
- dry/wet and bypass behavior;
- plugin placement decisions.

## Proposed core API

```rust
pub struct ProcessSpec {
    pub sample_rate: f32,
    pub channels: usize,
    pub max_block_frames: usize,
}

pub trait AnalogProcessor {
    fn prepare(&mut self, spec: ProcessSpec) -> Result<(), AnalogError>;
    fn reset(&mut self);
    fn process_interleaved(
        &mut self,
        samples: &mut [f32],
        frames: usize,
    ) -> Result<(), AnalogError>;
    fn latency_samples(&self) -> usize;
}

pub enum AnalogModel {
    Harmonics(HarmonicModel),
    Static(StaticColorModel),
    Hammerstein(HammersteinModel),
    Tape(TapeModel),
    Transformer(TransformerModel),
}
```

The enum should dispatch once per block. Each model owns its inner sample loop;
do not use virtual dispatch per sample.

All memory is allocated in construction or `prepare`. A block larger than the
prepared maximum returns a checked error and must never grow scratch storage on
the callback.

Continuous controls set targets and advance sample-rate-aware smoothers per
source frame, so output does not depend on callback partitioning. Internal
physical state such as flux, hysteresis, and sag belongs to the model;
host-facing parameter metadata does not.

## Realtime and buffer invariants

- Processing is in-place and overwrites every active sample.
- Return/consume exactly the host's `context.num_frames`.
- Validate `frames * channels` with checked arithmetic.
- Reject zero sample rate, zero channels, invalid maximum block size, unknown
  model IDs, and non-finite/out-of-range parameters before state mutation.
- Finite input and finite parameters must produce finite output.
- Define a non-finite audio policy that prevents one NaN/Inf from poisoning
  persistent model state; the proposed policy is to replace it with zero before
  state update.
- Reset clears filters, ADAA history, smoothers, envelopes, oversampling state,
  hysteresis/flux state, delay lines, and control interpolation state
  deterministically.
- No allocation, locks, blocking I/O, formatting, logging, filesystem access,
  or unbounded iteration in processing.
- Flush or avoid denormals.
- Channel-count and sample-rate changes require re-prepare/rebuild, not live
  state mutation.
- Structural controls are transactional: model, oversampling quality, topology,
  and latency-affecting options.
- Realtime controls include drive, amount, bias/tone where topology is fixed,
  output trim, and aligned mix.

## Oversampling, ADAA, and latency

Every nonlinear model generates content above Nyquist. At 48 kHz, the third
harmonic of 10 kHz lies at 30 kHz and aliases to 18 kHz.

Policy:

- use existing ADAA for supported memoryless functions with correct
  antiderivatives;
- use host-owned 2x/4x oversampling for dynamic, hysteretic, or component
  models;
- do not add a second internal resampler when the host wrapper already owns
  oversampling;
- do not assume ADAA makes arbitrary stateful nonlinearities alias-free;
- select the default factor from measured alias rejection and CPU data;
- treat factor/quality changes as structural graph changes;
- report wrapper latency exactly once.

Dry/wet mixing must align the dry path to the processed path. While an Analog
Color plugin instance is active, its reported latency remains invariant across
mix/bypass automation. A truly zero-latency disabled state requires removing
or rebuilding the stage off-thread.

Embedded coloration should follow the same rule: disabled at graph-build time
means no added path/latency; enabling it is structural. Once instantiated,
`amount = 0` uses latency-aligned dry output rather than silently changing the
node latency.

## Parameter and preset contract

Initial common surface:

- `enabled` — structural when it adds/removes a latent stage;
- `model` — structural, append-only enum;
- `quality` — structural Off/2x/4x or measured equivalent;
- `drive_db` — continuous;
- `amount` — continuous, 0 to 1;
- `character` — continuous macro mapped by the selected model;
- `bias` or `h2_db` — model-specific;
- `h3_db` — Harmonics model;
- `output_gain_db` — continuous;
- `mix` — continuous and latency-aligned;
- optional noise/hum/wow/flutter controls — disabled by default.

Do not expose every physical coefficient as a normal user control. Detailed
model parameters can live in advanced mode or immutable model definitions.

Each parameter addition or change must update:

- static parameter specification;
- runtime registration and cached metadata;
- setter and getter;
- schema and UI layout;
- serialization and default construction;
- engine settings/accessors/conversion;
- FFI/bridge exposure where applicable;
- preset round-trip and migration tests;
- realtime/structural update mode.

Existing Saturation mode indices and parameter IDs must not change.

## Placement in plugins

Provide two integration mechanisms.

### Standalone Analog Color plugin

Implement first so users can place the same model anywhere in a chain and make
level-matched A/B comparisons without modifying unrelated plugins.

### Embedded `AnalogColorStage`

Add only where placement has a deliberate signal-flow meaning:

- before a compressor detector: coloration changes detection and gain
  reduction;
- after gain reduction: coloration does not affect the detector;
- inside a feedback compressor loop: strong behavioral change requiring a
  plugin-specific design;
- before/after EQ: different frequency-dependent drive;
- output stage of a limiter or console model: requires peak/headroom review.

Do not duplicate business logic in UI crates. Plugin configuration and preset
logic remain in the canonical player/engine/plugin models.

## Measurement and model-fitting workflow

Hardware-specific work begins by identifying:

- exact device and revision;
- input/output interface and impedance;
- control settings;
- reference level/calibration;
- sample rate and capture chain;
- warm-up and operating conditions;
- repeatability across multiple passes or units.

Capture:

- low-level linear frequency and phase response;
- harmonic distribution versus input level and frequency;
- swept-sine harmonic impulse responses;
- two-tone intermodulation;
- transient/burst recovery;
- hysteresis or memory behavior;
- noise floor, hum, crosstalk, wow/flutter where relevant.

Fit low-order models first. Use held-out levels, frequencies, and programme
material for validation. Do not validate a fitted model only on the capture
used to estimate it.

## Spectral-analysis convention

For deterministic harmonic tests:

- prefer coherent sinusoidal records with an integer number of cycles;
- otherwise use a declared window and correct for its coherent gain;
- report sample rate, record length, window, one-sided/two-sided convention,
  FFT normalization, and output units;
- distinguish bin spacing from actual resolving power;
- inspect DC and Nyquist bins explicitly;
- use zero-padding only for plot interpolation, never as evidence of increased
  resolution.

For alias tests, compare base-rate output with a high-rate reference rendered
through a verified reconstruction/downsampling filter. Harmonic energy above
the base-rate Nyquist that folds into the audible band is alias energy, not
desired harmonic content.

## Verification matrix

### Deterministic functional tests

- exact or latency-aligned bypass;
- amount zero;
- silence and DC;
- positive/negative impulse;
- step and burst;
- sine at low, nominal, and high drive;
- non-finite audio and parameters;
- maximum block and maximum-plus-one behavior;
- reset compared with a fresh instance;
- sample-rate and channel-count re-prepare;
- mono/stereo/high-channel isolation;
- old-preset load and round-trip.

### Harmonic and frequency tests

Use at least:

- sample rates: 44.1, 48, 96, and 192 kHz;
- input levels: -36, -24, -18, -12, -6, and -1 dBFS;
- frequencies: 50, 100, 1k, 5k, and a safe near-Nyquist stress frequency;
- H2 through at least H10 where in band;
- THD and THD+N with clearly different definitions;
- DC offset and small-signal gain;
- two-tone IMD products;
- alias energy for Off/2x/4x and ADAA where supported;
- pre/post-filter magnitude, phase, and delay.

### Streaming tests

- one block versus fixed 32/128/512/2048-frame blocks;
- randomized callback partitions;
- partial final block;
- automation crossing block boundaries;
- no dependence on callback partition within documented numeric tolerance;
- no channel-state leakage in interleaved buffers.

### Stateful-model tests

- state convergence from rest;
- reset from saturated state;
- bounded response to extreme input;
- hysteresis loop direction/area where claimed;
- attack/recovery or sag time constants in milliseconds;
- sample-rate-independent physical time;
- deterministic behavior at an iteration cap/fallback.

### Realtime and performance tests

- allocation counter around representative non-empty processing;
- 1/2/6/12-channel workloads;
- Off/2x/4x quality;
- common and maximum block sizes;
- CPU/worst-callback report, not average throughput alone;
- denormal stress;
- no topology reconstruction through realtime setters.

### Listening comparison

Run level-matched, blinded comparisons between:

1. dry;
2. H2 only;
3. H3 only;
4. combined H2/H3;
5. static waveshaper;
6. Hammerstein/modelled version;
7. captured hardware reference where available.

Match loudness and peak headroom before judging. Record both preference and
discrimination; a louder result is not evidence of a better model.

## Phased implementation

### Phase 0 — Issue and evidence

- Create/identify the implementation issue.
- Confirm whether the first deliverable is generic coloration or emulation of a
  specific reference unit.
- Record the reference-level convention.
- Capture baseline CPU, harmonic, IMD, alias, latency, and preset behavior from
  the current Saturation plugin.
- Agree on naming and on measurable alias/performance budgets.

Exit criterion: approved scope and reproducible baseline artifacts.

### Phase 1 — `math-analog` foundation

- Add the crate in `math-audio`.
- Implement `ProcessSpec`, checked prepare/reset/process contracts, calibrated
  level mapping, and per-channel state containers.
- Implement the H2/H3 Harmonics model.
- Reuse `math-dsp` ADAA/filter/smoothing primitives.
- Add deterministic unit, spectral, streaming, and allocation tests.
- Add benchmark/report tooling.

Exit criterion: the baseline model is finite, bounded, block-independent,
allocation-free, spectrally characterized, and host-independent.

### Phase 2 — Extract static coloration

- Move reusable static curve mathematics out of
  `sotf-plugin-saturation` into `math-analog`.
- Preserve output behavior, mode indices, parameter IDs, preset loading, and
  host-owned oversampling.
- Keep plugin schema/UI/serialization in the SOTF wrapper.
- Decompose DSP state into focused sub-structs rather than expanding a plugin
  beyond the 30-field budget.

Exit criterion: existing Saturation behavior and focused tests remain
compatible; shared math has independent tests.

### Phase 3 — Standalone Analog Color plugin

- Add a dedicated plugin using the common model API.
- Start with Harmonics and Static models.
- Implement structural model/quality updates and latency-aligned mix/bypass.
- Wire canonical factory, catalog, engine settings/accessors/conversion,
  bridge/FFI surfaces, UI schema, presets, and migration tests.
- Add composed QA with non-silent multichannel material.

Exit criterion: users can make a trustworthy level-matched comparison anywhere
in the chain without modifying other plugins.

### Phase 4 — First richer model

- Implement a low-order Console/Preamp parallel-Hammerstein model.
- Fit it from either an openly documented target or a measured reference.
- Compare it directly against the H2/H3 and static baselines.
- Freeze fitted coefficients with provenance/version metadata.
- Validate held-out spectral, IMD, transient, and listening data.

Exit criterion: the richer model demonstrates repeatable behavior not explained
by output loudness or the H2/H3 baseline alone.

### Phase 5 — Selected embedded stages

- Choose plugins where internal placement has a clear physical/product reason.
- Document pre/post/feedback placement per plugin.
- Add structural enable/rebuild and fixed-latency mix behavior.
- Add plugin-specific detector, headroom, automation, and preset tests.

Exit criterion: each embedded use has an audible rationale and no duplicated
DSP or UI business logic.

### Phase 6 — Stateful tape/transformer models

- Proceed only with measurements/schematics and an agreed accuracy target.
- Add bounded state/iteration behavior and high-quality oversampling.
- Keep noise, hum, wow/flutter, and crosstalk modular and optional.
- Publish model limitations and validation evidence.

Exit criterion: model names and claims are supported by measured behavior,
including memory and frequency dependence.

## PR and review sequence

Keep changes reviewable and do not combine all phases:

1. `math-audio` PR: crate foundation plus Harmonics baseline.
2. Dedicated `sotf-plugin-saturation` PR: extraction/integration only, with no
   intentional sound or preset change.
3. Dedicated Analog Color plugin PR.
4. One PR per richer model.
5. One PR per embedded plugin integration where signal placement differs.

Any PR touching `engine/` or `sotf-plugins/` must run through the required
`pr-review-toolkit:code-reviewer` workflow before merge. Reviews must cover
correctness, algorithmic edge cases, error handling, realtime behavior, and
concrete regression tests.

## Risks and mitigations

### Aliasing mistaken for “analog detail”

Mitigation: oversampled-reference alias metrics and explicit Off/2x/4x
comparisons.

### Louder output winning listening comparisons

Mitigation: calibrated output trim, loudness/peak matching, and blinded tests.

### Model names overstating accuracy

Mitigation: distinguish mathematical curve, “-style” coloration, measured
black/grey-box model, and component model in metadata and documentation.

### Dynamic controls becoming block-size-dependent

Mitigation: per-source-frame smoothing and randomized callback-partition tests.

### Hidden latency changes

Mitigation: structural quality/enable changes, graph rebuild, one oversampling
owner, and aligned dry/bypass paths.

### Stateful models poisoning all future audio after NaN or failed convergence

Mitigation: sanitize non-finite input before state update, cap iterations,
provide finite fallback, and stress reset/recovery.

### Library abstraction becoming too broad

Mitigation: start with Harmonics plus one common chain; add abstractions only
after the second concrete model proves the shared boundary.

### CPU explosion at high channel counts

Mitigation: block-level enum dispatch, prepared buffers, bounded model order,
quality modes, allocation tests, and 1/2/6/12-channel QA.

2. Confirm `-18 dBFS` as the default 0 VU reference.
3. Choose the first richer target: generic Console/Preamp or a specific

4. Decide whether 2x or 4x is the default quality from Phase 0 measurements.
5. Define an explicit alias-energy and CPU budget on the selected benchmark

6. Decide which plugin, if any, should receive the first embedded stage after
   the standalone plugin proves the API.

## Definition of done

The overall initiative is complete only when:

- simple H2/H3, static, and richer models share one tested core API;
- every model has truthful naming and documented signal equations;
- finite input produces finite output and reset is deterministic;
- callback partitioning does not change documented behavior;
- steady-state processing is allocation-free and bounded;
- oversampling has one owner and latency is correctly reported/aligned;
- presets/schema/UI/engine/bridge surfaces remain in exact parity;
- existing Saturation presets remain compatible;
- alias, harmonic, IMD, transient, and performance reports are reproducible;
- richer models outperform the level-matched H2/H3 baseline on their stated
  measured target, not merely by being louder;
- required focused and workspace checks pass;
- required SOTF plugin/engine code review is complete.
